# Ограничения и остаточные риски

## Качество

- **LLM-путь не проверен вживую.** Форма запроса сверена с текущим API (модель, `output_config.format`, `effort`, beta серверного fallback), и он покрыт тестами на фейковом клиенте. Реального вызова не было. Проверка — `python -m ml.live_smoke`.
- **Разметка `eval/gold_dev.json` сделана моделью, а не человеком,** и правила подгонялись на тех же 10 диалогах. Accuracy 97% для rule-based — оценка на обучающих данных.
- **Лексиконы правил собраны по DEV.** На контрольном наборе они могут промахиваться, поэтому основной путь — LLM, а правила дают подсказки и второе мнение.
- **Без ключа новый критерий без `keywords` получает N/A**, а его вес перераспределяется. Такой критерий отмечается `needs_review: no_rule`, но итог при этом выглядит уверенным. Перед заменой критерия без ключа заполните `keywords` в редакторе.
- **Бесплатный провайдер (Gemini) не измерен на нашей разметке.** Открытые и бесплатные модели заметно слабее на казахском (KazMMLU); сравнение по языкам — `eval.run_eval` на `gold_human.json`. Если на KZ модель хуже правил, это видно в отчёте по языкам. Данные бесплатного тарифа могут использоваться провайдером — для реальных (не обезличенных) диалогов нужен платный тариф или локальная модель.
- **`confidence` — это уровень, а не вероятность.** Он выводится из явных сигналов (согласие методов, fallback, самооценка модели). Калибровки (ECE, Brier) нет: для неё нужна независимая человеческая разметка.
- **Эмоции, намерения, дикцию и интонацию система не оценивает.** Она работает только по тексту транскрипта, звук не анализируется (ASR не требуется по ТЗ).
- **В rule-based режиме review почти не срабатывает:** у одного метода нет второго мнения. На gold оба промаха правил не были отмечены (см. [evaluation.md](evaluation.md)).

## Надёжность

- **Batch выполняется в потоке процесса сервера.** При рестарте задача получает статус `interrupted`, повторный запуск досчитывает остаток. Внешней очереди нет — сознательно.
- **SQLite с глобальным локом на запись.** Этого достаточно для сотен диалогов и одного сервера, но не для горизонтального масштабирования.
- **Миграций схемы нет:** таблицы создаются через `CREATE TABLE IF NOT EXISTS`. Новая таблица `llm_cache` добавляется так же, совместимо со старой БД.

## Security review (итерация 2026-11-07)

| Проверка | Результат |
|---|---|
| Секреты в git и истории | Чисто: `.env` и `*.db` в `.gitignore`, в истории только фейковые `sig=SECRET` из тестов |
| Секреты в логах | Логи `httpx` подавлены (URL организаторов содержит `sig`). Ошибки LLM пишутся в лог только типом исключения |
| SQL injection | Все запросы параметризованы; `json_extract` использует фиксированные пути |
| **Path traversal** | **Найден и исправлен:** `id` чек-листа от клиента попадал в имя файла (`../../evil-v1`). Есть регрессионный тест |
| SSRF | Сервер скачивает только `audio_url` из данных организаторов. Ad-hoc оценка не принимает `audio_url` |
| Prompt injection | Транскрипт выделен как недоверенные данные и не может закрыть блок; ответ модели ограничен JSON-схемой и enum-ответами; итог считает код |
| CORS | Разрешены localhost/127.0.0.1 и `null` (file://). Для локального демо это нормально, для продакшна `null` нужно убрать |
| Авторизация, rate limiting | Нет: по ТЗ для демо не нужны. Для продакшна обязательны, в первую очередь на `/ingest`, `/evaluate/batch` и `/review` |
| Ограничение размера запросов | Явного лимита нет. Для продакшна — лимит тела на прокси и длины транскрипта |
| Персональные данные | Данные организаторов обезличены. При включённом LLM транскрипты уходят в Anthropic API — для реальных данных нужно согласование |
